## 1. 目的

本基线在**代码尚未存在**的时点建立，用于让后续的 `Baseline Role Alignment` 检查
有据可依。后续对齐检查应使用它来回答：

- 「当前实现是否仍服务于已确认的产品需求？」

本文件是**证据，不是权威**；权威是已批准的设计规格
`docs/aegis/specs/2026-09-10-mental-math-app-design.md`。

## 4. 产品 / 需求基线

### 4.1 当前真相

- **需求来源**：用户在会话中直接给出的十项功能描述。无其他外部需求文档。
- **目标状态**：可自部署的速算练习应用，前后端分离，Android 为主、开发期浏览器调试。
- **目标用户**：自部署者本人及其邀请的小群体（多用户 + 一个管理员）。
- **使用场景**：创建/订阅速算练习项目 → 逐轮练习（自带键盘、可暂停）→ 查看总结与
  错题 → 消费按项目的日/周/月统计。
- **功能需求项**：见规格 §16 需求可追溯性表（十项，逐项映射到章节）。
- **交付/过渡需求**：本地可测；打 tag 触发 CI 产出 Docker 镜像，推送 ghcr 并作为
  release 附件分发。
- **验收标准**：规格 §13 的 A1–A10。
- **已固定的成功证据**：`go test ./...` 与 `flutter test` 通过；浏览器可完整走通
  `注册→建项目→练习→总结→错题重练→统计→分享订阅`；tag 后镜像可达。

### 4.2 不可协商项

1. **第一个注册用户即为管理员**（功能1）。
2. **注册开关关闭时，首个用户仍必须能注册**，否则全新部署自我锁死。
3. **删除项目必须级联删除所有人的答题记录**（功能8）。
4. **作者修改项目配置后，订阅者的项目同步改变**（功能5）——单一行共享，不做快照复制。
5. **关闭 App 不保存、不可续做**（功能6，经 D6 确认）。
6. **打错必须立即反馈并出现「下一题」按钮**（功能9）。
7. 底栏固定三 Tab：练习 / 统计 / 我的（功能3）。

### 4.3 产品非目标

- iOS 发布；离线优先；题目市场与审核；邮件找回密码；管理员后台（D7）；
  未完成练习续做（D6）；`--split-per-abi` 分 ABI 产物；应用内自动更新。
  （**注**：APK 正式签名与签名构建**已在范围内**，见 D17/D18 与规格 §10.3。）

## 5. 架构 / 运行时边界基线

### 5.1 当前真相

- **规范 owner 划分**：后端 `api / service / store / rules / auth` 五层；
  前端 Flutter 单工程。前后端仅通过 HTTP/JSON 通信。
- **契约 / 事实源边界**：
  - 做题事实源 = `practice_round` + `attempt` 两张表；**统计是派生态，不是第二事实源**（D5）。
  - 题面与答案以**快照**存于 `attempt`，规则源码**不是**历史题目的重建依据。
  - 规则契约边界 = 作者只写 `function generate(cfg)` 返回 `{q, a}`（D1/D11）。
- **依赖方向**：`api → service → store`；`service → rules`（规则引擎被业务调用，
  不反向依赖）。前端依赖后端 HTTP 契约，不依赖后端内部结构。
- **客户端连接边界**（2026-09-11 增补，见 ADR-0006）：服务端地址是**客户端本地设置**
  （`serverAddressProvider`），不是构建期常量。客户端只支持明文 HTTP 与 HTTPS；
  明文放行写在 `network_security_config.xml`，因为后端未实现 TLS。
  当前数据作用域 = 「服务端地址 + 登录令牌」的组合（`dataScopeProvider`）：
  任一方变化即作废项目/统计/订阅数据。**切换服务器必然清除登录态**。

### 5.2 架构不可协商项

1. **规则沙箱必须同时设置 `SetMaxCallStackSize` 与 `Interrupt` 超时**。
   实测证明：仅设其一即存在挂死/耗尽的窗口；两者缺一不可。
2. **规则保存前必须通过校验**（规格 §5.3），因为坏规则会连坐所有订阅者。
3. **级联删除只有一条规则**：`(project, user)` 关系终止 ⇒ 该用户在该项目下的
   `practice_round`/`attempt` 消亡。不得为「作者删项目」与「订阅者退订」各写一套逻辑。
4. **统计不得物化**（D5）：必须可从 `practice_round`/`attempt` 实时推导。
5. **不建规则 VM 池**：实测冷启动 23.7µs/题，不足以支撑池化的复杂度。
6. **判分路径不得出现浮点**（D15）：有理数一律交叉相乘的整数运算比较。
7. **输入清洗表只有一个 owner（服务端）**：客户端只能应用服务端下发的清洗表，
   不得内置清洗策略；不得引入 NFKC 等 Unicode 归一化库。
8. **`server_is_correct` 是唯一权威判分值**（D16）：`client_is_correct` 仅供即时反馈
   与分歧告警；统计一律基于前者。二者不一致必须留痕，不得静默覆盖。

### 5.3 架构非目标

- 微服务拆分、消息队列、缓存层（Redis 等）。
- 多实例/水平扩展（单进程 + SQLite 单文件是刻意选择）。
- 规则热加载/灰度发布。

## 6. Owner / 契约快照

| 关注面 | 规范 owner | 契约形态 |
|---|---|---|
| 出题逻辑 | `internal/rules` | `generate(cfg) → {q,a}` |
| 判分正确性 | `internal/service`（服务端重算，D13） | 归一化比较函数为**唯一**判分实现 |
| 输入清洗规则 | **服务端**（随 `/rounds/start` 下发，D15） | 字符映射表为数据；客户端只应用 |
| 判分权威值 | `attempt.server_is_correct`（D16） | `client_is_correct` 仅作反馈与告警 |
| 账号与口令 | `internal/auth` | 不透明 token，哈希入库 |
| 做题事实 | `internal/store` | `practice_round` / `attempt` 两表 |
| 统计派生 | `internal/service` | 读时聚合，无独立存储 |
| 项目归属与订阅 | `internal/store` | `project.owner_id` + `subscription` 表 |

### 边界缺口

- ~~**判分归一化的唯一定义点**尚未落地~~ → **已由 D15 关闭**（规格 §5.5）。
  收敛措施：答案域收敛为「有理数 / 规范文本」两种信封；有理数比较用交叉相乘的
  **纯整数运算**（Go `math/big` ↔ Dart `BigInt`）；**输入清洗表由服务端单一下发**，
  客户端只应用数据；**不使用 NFKC 类 Unicode 归一化库**（Go 与 Dart 生态语义未必一致，
  是最易忽略的漂移源）。
  **约束方式**：CI 语料门禁（≥10,000 条边界向量，Dart 必须逐例向 Go 对齐，
  分歧即失败）+ 生产期 `client_is_correct` / `server_is_correct` 分歧告警
  + 可基于 `user_input` 与信封**全量重算**历史。
  残余：技术上仍是两份实现，但语义被上述六重措施约束（规格 §5.5.8 已诚实记录）。
- **分享 token 的订阅者预览流程**尚未明确（点开链接先看再确认，还是直接订阅）
  —— 留给实施计划细化。

## 7. 当前状态与风险

- **当前阶段**：已实现并发布（v0.0.2；v0.0.3 待发布）。P0–P7 全部交付，
  规格 §13 的验收标准除「APK 真机覆盖安装」外均已验证。
- **已知风险**（详见规格 §14）：R1 契约难改、R2 坏规则连坐、R3 goja 无内存上限、
  R4 退订不可逆、R5 客户端持有答案、R6 开发期 CORS。
  另有实现期发现的 R7：**明文 HTTP 放行**（ADR-0006）——后端未支持 TLS，
  局域网流量可被嗅探；后端支持 TLS 后应收紧为按域名放行。
- **已验证的原假设**：V1 `modernc.org/sqlite` 纯 Go 可用性（实测通过）；
  V4 Dart `BigInt` 与 Go `math/big` 逐例一致（13,872 条语料钉死）。
- **工程教训（值得留档）**：「构建成功 + 镜像已推送 + 签名正确」都不等于
  「应用能工作」。release APK 曾因缺少 INTERNET 权限而无法联网，
  却通过了构建与验签；Docker 镜像曾因 `/data` 属主问题而无法启动，
  却通过了构建与推送。二者都是靠**真正把它跑起来**才发现的
  （release.yml 的 smoke job 与权限解包核对）。

## 8. 对齐用途

- 需判断**「该不该做这个功能」** → 读 §4 产品 / 需求基线。
- 需判断**「该放在哪一层、谁是 owner、可否加冗余」** → 读 §5 架构 / 运行时边界基线。
- 需求与架构同时存疑（例如新增一种统计维度既改产品语义又改事实源边界）→ 报
  `scope: both`。

## 9. 兼容边界（早期开发期不得破坏）

1. 规格 §6.1 的五条核心不变量。
2. 规格 §5.2 的沙箱四配置齐全性。
3. `(project, user)` 单一级联规则。
4. 题面快照与规则源码的解耦（改规则不得改历史）。
5. 判分路径无浮点 + 清洗表单一下发（§5.2 第 6/7 条）。
6. `server_is_correct` 的权威地位与分歧留痕（§5.2 第 8 条）。
